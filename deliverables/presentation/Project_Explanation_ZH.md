# 超市收银系统项目详解

这份材料帮助你理解 ProjectPos_2026 的实际实现，并能沿着代码说明一次销售和退货如何完成。项目采用 Java、Spring Boot、Maven、Thymeleaf、Spring Data JPA、Hibernate 和 MySQL，核心用例是销售处理与退货处理。阅读时建议同时打开项目，按照文中类名寻找对应方法，再用独立录屏商品完成一次练习。

## 一 项目整体与业务目标

销售点系统就是收银员使用的收银软件。本项目解决的主要问题是：商品数量、收款金额、找零金额、销售记录和退货记录需要保持一致。没有系统校验时，可能出现库存不足却成交、少收现金、超出购买数量退款，或者商品改价后历史小票金额跟着改变等问题。

项目面向本机上的可信收银员，没有实现账号登录、角色权限、银行卡支付、独立税费、优惠券或钱箱硬件。现金由收银员实际收取或退还；系统记录金额并计算找零或退款。接受退货前，还需要收银员判断商品是否适合重新入库。当前程序将接受的退货数量加回可售库存，没有实现破损商品的单独库存。

销售处理从选择商品开始。收银员可以把同一种商品多次加入购物车，程序合并数量并检查可用库存。页面展示商品明细和合计。输入足够现金后，服务再次检查商品、数量、库存和付款，保存销售及明细、扣减库存，再跳转到小票。现金少于合计时，页面显示英文错误并保留购物车。

退货处理从原销售小票开始。收银员选择这张小票中的一条购买明细，填写数量和原因。服务检查剩余可退数量，按照该明细保存的原单价计算退款，增加库存、累计已退数量，并新增退款记录。一张小票有多个商品时，需要逐条提交退货。

项目没有根据商品条码自动连接扫码枪；页面通过下拉框选择商品。小票由网页展示，并提供浏览器打印按钮。能打开打印功能不等于已经完成了实体热敏打印机或钱箱联动测试。

## 二 技术各自负责什么

### Java 与 Spring Boot

Java 是实现业务规则的语言。`Product`、`Sale`、`SaleItem` 和 `ReturnRecord` 都是 Java 类，它们保存状态并提供与状态相关的方法。`BigDecimal` 用于金额计算，避免把十进制金额交给二进制浮点数后出现难以解释的舍入误差。

Spring Boot 负责组织和启动应用，读取配置、建立依赖对象并启动内嵌网页服务器。入口是 `ProjectPos2026Application.main`。控制器、服务和仓库通过构造方法接收依赖，不需要在每个按钮处理方法中手动创建整套对象。项目的 Spring Boot 父版本为 4.1.1，编译目标为 Java 17；此前实际验证使用的是 JDK 21。编译目标与运行时 JDK 版本是两个不同概念。

### Maven

`pom.xml` 描述依赖和构建配置。Maven 获取所需库、编译代码、运行测试，再把程序打包。`mvnw.cmd` 是项目中的包装器入口，本项目使用 Maven 3.8.5。`clean test` 先清理构建输出再测试；`clean package` 还会生成可运行的 JAR。它们不会因为名字里有 clean 就删除 MySQL 的业务数据库。

### Thymeleaf 与 MVC

Thymeleaf 把服务端提供的数据填进 HTML 模板。比如 `receipt.html` 根据销售对象显示小票，`sale-form.html` 根据购物车明细显示合计。浏览器最终接收的是渲染后的 HTML，而不是直接读取 Java 对象或数据库密码。

MVC 将页面展示、请求协调和数据模型分开。本项目在 MVC 基础上进一步分成控制器、服务、仓库和实体：控制器处理请求与页面跳转；服务组织业务用例和事务；仓库查询数据库并申请锁；实体维护业务状态与规则。控制器读取服务返回的实体数据用于渲染，因此实际代码采用允许跨层读取的宽松分层，不应宣称所有依赖都严格只能访问紧邻下一层。

### Spring Data JPA 与 Hibernate

JPA 是对象持久化的规范，定义实体、关联等映射方式。Spring Data JPA 为仓库接口提供常用持久化能力，并可按方法名称生成查询。Hibernate 是本项目实际使用的 JPA 实现，负责把实体变化与数据库记录同步。三者分别是规范、开发支持和实现层，答辩时需要说明各自位置。

例如，`ProductRepository` 继承 `JpaRepository<Product, Long>`，因此可以使用常用的保存、按编号查询等方法。`findByBarcode` 按条码查询；`findLockedById` 使用显式查询和悲观写锁。仓库接口本身没有手写所有 SQL，底层仍会执行数据库语句。

### MySQL

MySQL 保存应用关闭以后仍需保留的商品、销售和退款记录。应用库名为 `pos_2026_db`。四张业务表都已在真实 MySQL 8.0.44 中验证为 InnoDB。默认自动化测试使用 H2；另一个配置使用独立的 `pos_2026_test_db` 执行真实 MySQL 测试，避免把自动化测试数据混入应用库。

## 三 项目目录与关键文件

`src/main/java/com/example/projectpos_2026` 是主要 Java 源码目录。`controller` 包包含网页控制器、表单对象、会话购物车和网页配置。`service` 包实现商品维护、销售和退货用例。`repository` 包包含持久化接口。`entity` 包包含四个实体。`exception` 包提供共享业务异常，避免实体依赖上层服务包。

`ProductController` 处理商品页面。`SaleController` 管理购物车、结账、销售列表、查找小票和展示小票。`ReturnController` 处理退货提交。`WebConfiguration` 固定英文界面语言，并通过拦截器检查改变数据的 POST 请求中的会话令牌。`WebErrors` 负责统一处理部分错误并返回友好的页面。

`ProductForm` 位于 `controller` 包，是接收商品表单的对象。它使用非空、价格范围、库存范围和小数位等约束。项目没有独立的 dto 包，不要在答辩中指认一个不存在的目录。`SaleService.CartLine` 与 `ReturnService.ReturnView` 是 Java 记录类型，分别提供购物车展示和退货记录展示需要的数据。

`ShoppingCart` 也位于 `controller` 包。它保存在 HTTP 会话中，只保存商品编号、数量和本次结账标识，不保存需要长期托管的 JPA 实体。它使用有序映射和同步方法，使同一会话的操作更可控；购物车改变后会更新结账标识，旧页面提交可能被判为过期。

`src/main/resources/templates` 存放 HTML 模板。`products.html` 是商品列表，`product-form.html` 是商品新增或编辑表单，`sale-form.html` 是购物车与收款页面，`receipt.html` 是小票、退货表单和退款记录，`sales.html` 是销售列表和查找入口，`fragments.html` 保存重复使用的导航与提示区域。`static` 存放样式表等静态资源。

`application.properties` 保存数据源地址、用户名占位配置、JPA 和服务器选项。`spring.datasource.password=${DB_PASSWORD}` 表示从环境变量取得密码，实际密码没有写入 Git 跟踪的配置。`spring.jpa.open-in-view=false` 使网页渲染阶段不继续依靠开放的持久化上下文随意加载数据，因此小票查询使用实体图预先加载明细。

`pom.xml` 配置依赖、Java 目标版本及 Spring Boot 插件。`src/test` 保存测试代码与测试数据源配置。`target` 是构建输出，`docs/evidence` 保存真实验证证据，`deliverables` 保存提交材料。`.local` 保存本机临时运行信息和被忽略的凭据，不应上传到公共仓库。

## 四 点击销售按钮以后发生什么

### 打开商品页和销售页

浏览器访问 `/` 时，`ProductController.home` 返回重定向，把用户带到 `/products`。`ProductController.list` 调用 `ProductService.all`，后者调用仓库按名称取得商品列表，把数据放进模型后由 `products.html` 渲染。因此当前“首页”实际显示商品列表，没有另一个单独的首页仪表盘。

点击导航中的“New sale”后，浏览器发送 `GET /sales/new`。`SaleController.newSale` 从会话取得购物车，调用 `SaleService.preview` 查询当前商品信息，创建展示用明细，并把各明细小计相加。此时只是在展示购物车，尚未创建销售记录，也没有扣减数据库库存。

### 加入购物车

点击“Add item”后，浏览器提交 `POST /sales/cart/add`。`SaleController.add` 接收商品编号和数量，调用商品服务查询商品，并检查它是否仍可销售。随后 `ShoppingCart.add` 合并已有数量，检查正数、单品最多一万件、最多一百种商品及当前可用库存等条件。

购物车改变以后生成新的结账标识。控制器重定向回销售页，页面重新计算合计。加入购物车时的库存检查可以尽早提醒用户，但其他收银操作仍可能在此后消耗库存，所以真正付款时必须再检查。

### 提交现金付款

点击“Complete sale”后，浏览器提交 `POST /sales/checkout`，参数包含 `cash` 和 `checkoutKey`，以及隐藏的会话校验令牌。拦截器先检查令牌，控制器再检查提交的结账标识是否与当前购物车一致。这里的会话校验令牌、结账标识和数据库销售编号用途不同，不能混为一谈。

`SaleController.checkout` 调用 `SaleService.checkout`。方法上的 `@Transactional(isolation = Isolation.READ_COMMITTED)` 定义该用例的事务。服务验证结账标识，查询是否已有同一请求的销售；若已完成则返回已有销售，避免再保存一次。

随后检查购物车不为空、商品与数量合法、现金小数位与金额范围合法。服务按商品编号排序，依次通过 `ProductRepository.findLockedById` 获得产品行的悲观写锁。排序可降低多个结账按相反顺序争用相同商品产生死锁的风险，但不能解释成系统已证明完全不会死锁。

锁定后再次检查商品存在、有效状态和库存，并由 `Sale.addItem` 创建 `SaleItem`。`SaleItem` 在这一步复制商品名称、条码和原单价；它的 `getSubtotal` 用原单价乘数量，`Sale` 将小计累加成总额。等待锁以后，服务再次检查结账标识是否已对应一笔完成的销售。

现金不足会抛出 `BusinessException`，控制器将错误放入重定向提示，保留购物车。现金足够时，`Sale.recordPayment` 保存实收现金并计算找零；`Product.decreaseStock` 扣减库存；`sales.saveAndFlush` 保存销售与级联明细并把变化发送给数据库。服务方法成功返回后事务提交。flush 与 commit 的概念不同：flush 把变化同步到数据库，事务仍可能因后续错误回滚。

控制器清空购物车并跳转到 `/sales/{id}`。`SaleController.receipt` 查询带明细的销售及退款记录，生成退货请求标识，最后由 `receipt.html` 显示小票。成功后使用重定向有助于减少普通刷新造成的重复提交，但业务层仍需要自己的重复请求保护。

### 原子性与实体更新

事务中的产品是由仓库查询得到的受管理实体。调用 `decreaseStock` 改变它的属性后，Hibernate 可以通过脏检查在刷新或提交时写回数据库，因此销售服务没有必要为每个已管理的产品再显式调用一次 save。自动化测试验证了失败付款不会留下销售记录或部分扣库存。

举例：两件米单价 6.50 加一件牛奶单价 3.80，合计为 16.80。现金 20.00 减合计 16.80，找零为 3.20。用独立录屏商品时，初始库存 10 和 10，成交后为 8 和 9。这是接下来录屏的预期结果；录屏前尚未自动创建这笔新销售。

## 五 点击退货按钮以后发生什么

### 原销售与购买明细

收银员可以从“Transactions and returns”打开销售列表或查找销售编号。`SaleController.lookup` 先验证这笔销售存在，再跳转到小票页。退货表单中的购买明细来自这张小票，不是任意从商品目录选一个商品就能退款。

点击“Record return and cash refund”后，浏览器提交 `POST /sales/{saleId}/returns`。`ReturnController.process` 接收销售编号、购买明细编号、退货数量、原因和请求标识，交给 `ReturnService.process`。控制器负责页面流程，退款校验与数据库事务集中在服务中。

### 校验与锁定顺序

退货服务先验证请求标识，检查是否已完成过同一请求，再验证数量为一到一万以及原因长度为一到二百个字符。`SaleItemRepository.findLocked(itemId, saleId)` 同时使用明细编号和销售编号查询并获得悲观写锁，因此另一个销售的小票明细不能借用到当前销售上。

获得明细锁后，再次检查请求是否已经处理。`SaleItem.getReturnableQuantity` 返回购买数量减累计已退数量。退货超过这个差值时抛出业务异常。接着锁定对应商品行，调用 `Product.restoreStock` 检查补回后的库存不超过上限，调用 `SaleItem.recordReturn` 增加累计已退数量，再保存新的 `ReturnRecord`。

`ReturnRecord` 构造方法用原 `SaleItem.unitPrice` 乘接受数量计算退款。它没有读取当前商品目录里的价格，因此商品改价后，旧购买明细的退款仍遵循原价。即使商品后来停用，已发生购买仍可以按当前退货规则处理；商品停用主要限制新的销售。

### 提交结果与重复请求

库存、明细中的已退数量和退款记录位于同一个事务。正常成功时一起提交，异常时一起回滚。控制器回到原小票页，显示退款提示和退款记录列表。如果重复发送同一个已完成请求标识，服务返回之前的退款记录，不再增加库存或再次记账。

页面每次重新展示都可能生成新的退货请求标识，因此“同一请求去重”和“累计退货数量限制”共同发挥作用：前者处理同一次请求的重试，后者处理用户使用新表单继续退货。程序没有实现现金转账接口，收银员仍需实际把现金交还顾客。

录屏的例子是先尝试退三件米，因只买两件而失败；再接受退一件，退款 6.50，米库存由 8 恢复到 9，牛奶仍为 9。小票上的米还可退一件。不要把已经退过的旧销售当作每次都能重新执行同一演示的空白数据。

## 六 数据库与数据一致性

### 连接配置与表映射

默认连接地址为本机 3306 端口上的 `pos_2026_db`，用户名默认从配置读取为 root，密码来自 `DB_PASSWORD`。也可以通过 `DB_URL` 和 `DB_USERNAME` 覆盖地址与用户名。浏览器页面不需要也不应该接触这些数据库凭据。

实体上的 `@Entity` 表示这是持久化对象；`@Table` 指定表名。四个实体都使用 `id` 作为主键，并使用数据库自增生成标识。`@Column` 描述非空、长度以及金额精度等约束。金额列使用十进制定点类型对应的精度与两位小数映射。

`products` 保存条码、名称、单价、当前库存、有效状态和版本。条码有唯一约束。库存是商品上的汇总数量，没有为每件实物建立单独记录，也没有独立的仓库模块。

`sales` 保存一次销售的时间、合计、现金、找零和唯一结账标识。`sale_items` 保存购买数量、累计已退数量以及原商品名称、条码、单价。它通过 `sale_id` 指向销售，通过 `product_id` 指向商品。`return_records` 通过 `sale_item_id` 指向原购买明细，保存退货数量、退款、原因、时间和唯一请求标识。

一笔销售对应一条或多条购买明细；一个商品可以被多条购买明细引用；一条购买明细可以对应零条或多条退货记录。数据库里的关联约束和服务中的数量校验解决不同问题：外键保证引用关系有效，但“累计退货不超过购买数量”仍由业务规则维护。

### 为什么旧表单不能直接覆盖库存

`Product` 使用 `@Version`，编辑表单也携带读取时的版本。`ProductService.update` 锁定商品后把表单版本与当前版本比较。如果用户打开编辑页后，另一笔销售改变了库存，旧页面的更新会被拒绝并要求重新加载。否则旧库存值可能把刚扣掉的数量覆盖回去。

悲观行锁用于协调并发交易正在修改的数量；版本校验用于识别过期编辑页面。两者针对不同冲突。不能因为页面看起来只有一个收银员，就忽略浏览器重复标签页或并发请求。

### 可用于展示的只读查询

在数据库工具中执行 `SHOW TABLES;` 可以查看四张表。`SELECT id, barcode, price, stock FROM products;` 可以展示商品库存。使用 `SELECT id, total, cash_paid, change_due FROM sales;` 查看销售金额，使用 `SELECT sale_id, product_name, quantity, returned_quantity FROM sale_items;` 查看购买与已退数量，再查看 `return_records` 中的退款。

这些查询需要先选中正确的应用数据库。不要执行删表或清库来“恢复演示”。项目的 `spring.jpa.hibernate.ddl-auto=update` 用于这个简单课程环境中的表结构更新，不等于正式的数据库迁移版本管理或自动备份。

## 七 软件工程概念与本项目的对应关系

Scrum 是以短周期计划、可交付增量、检查和调整组织工作的框架。本项目由一个人完成，采用其中的待办排序、增量实现和验证反馈方法。不能虚构多人站会、评审通过或已经跨越多天的冲刺。

产品待办列表是按价值与优先级组织的工作集合。项目的原列表共有十八项。史诗是较大的业务主题，例如销售处理；用户故事描述使用者、需求和目的，例如“作为收银员，我希望系统计算正确找零，以便把现金交还顾客”。用户故事需要落实成代码和验收依据，而不是只写一句话。

冲刺是固定时间长度的工作周期。作业允许三天或一周的短周期。材料中的三天窗口是后续复查与提交安排，不是已经发生的开发历史。本次代码增量确实按商品、销售、退货和集成顺序推进，但实际记录集中在同一天。

燃尽图展示剩余工作随时间的变化。本项目使用真实时间戳统计原十八项待办的剩余项数。它不是工时，也不是故事点，不能用来声称各项耗时相同。PPT 使用包含最终验证检查点的记录；原技术报告中的图明确保留了更早的检查点截止时间。二者使用的真实记录范围不同，不能把它解释成数据矛盾。新增的第四阶段录屏材料不属于原十八项待办。

用例图说明系统边界、参与者和目标。收银员是直接操作软件的参与者；销售处理和退货处理是核心目标。完全展开用例进一步说明触发条件、前提、正常步骤、成功保证以及异常分支，例如付款不足如何处理。

领域模型描述业务概念、属性和关联，例如销售包含购买明细。设计类图进一步描述软件实现中的类、方法、字段类型和依赖。领域模型不应直接被画成带所有数据库注解和控制器方法的程序清单。包图则在更高层说明控制器、服务、仓库、实体与共享异常包如何依赖。

## 八 Git 与 GitHub 的真实使用

Git 在本地记录版本。仓库包含提交对象、分支引用和工作区状态。提交相当于一次有说明的版本记录；分支是指向一条开发历史位置的引用，不是再建立一个不同项目。合并把另一个分支的工作接入当前分支。本项目使用保留分支边界的合并提交。

初次检查时，项目目录没有 Git 仓库。移除被跟踪配置中的明文凭据以后，才建立本地基线。商品、销售和退货分别有有意义的功能提交；原有代码没有被重新建项覆盖。远程仓库由你在 `0ShaoYifei/ProjectPos_2026` 建立，里面已有的初始 README 提交也通过合并保留，没有强制覆盖。

GitHub 是托管远程仓库的平台。此前命令行认证失败后，你登录 GitHub Desktop，再由 Desktop 推送分支。之后真实远程哈希与本地核对一致。第四阶段开始时，主分支为 `1316a7c`，文档分支为 `ce62819`；新制作的演示材料使用额外的 `feature/presentation` 分支。这些是检查点，后续提交会让当前最新哈希继续改变。

录屏时先展示真实仓库地址，再在主分支的提交列表中说明功能提交和合并记录，然后展示保留的商品、销售、退货和文档分支。若演示材料分支已上传，也可以一起展示。GitHub Desktop 中“No local changes”仅说明没有未提交修改；如果仍有“Push origin”提示，还存在本地已提交但未上传的版本。

## 九 测试结果应该怎样理解

单元测试通常针对较小的代码单元，隔离其外部依赖。本项目的主要服务测试通过 Spring Boot 环境和真实仓库访问数据库，因此更准确地说，它们主要是业务集成测试，并非全部都是用模拟对象完全隔离的纯单元测试。不要把测试方式解释成每个类都有单独的纯单元测试。

测试总数为二十一项：一项上下文启动测试、四项商品测试、八项销售测试、六项退货测试和两项并发测试。同样的二十一项先在 H2 上通过，又在独立的真实 MySQL 测试库上通过。这是同一组场景在两种数据库上的验证，不是四十二个不同场景。

商品测试覆盖创建与更新、条码重复、无效价格与库存、过期编辑。销售测试覆盖多个商品的总额和找零、精确付款、库存不足、现金不足、空购物车与非法数值、无效商品、重复结账和历史小票价格。退货测试覆盖原价退款、累计超退、非法原因和明细归属、重复请求、过期标识及库存上限导致的回滚。

两项并发测试分别检查两个线程争抢最后一件库存、以及两个线程争退同一最后可退数量的情况。它们提供了特定并发情形的证据，不是大规模压力测试，也没有得到每秒交易数或长期稳定性指标。

真实浏览器另外执行了十三项检查，包括正常小票、付款不足、库存不足、超量退货、重复退货、表单与会话令牌等。MySQL 查询确认四张表及原销售 POS-1、退款 RET-1 和库存变化。原示例总额为 16.80、现金 20.00、找零 3.20，退一件米退款 6.50。

`BUILD SUCCESS` 表示这次 Maven 命令执行的构建步骤成功；测试日志的 Tests run、Failures、Errors 和 Skipped 才说明测试数量、断言失败、运行错误和跳过数量。`BUILD FAILURE` 要继续看具体原因，可能是依赖下载、编译、测试断言或环境问题，不能一律解释成业务规则错误。

已记录的问题包括基线离线构建缺少缓存依赖、第一次 MySQL 配置参数被 PowerShell 拆分，以及最初浏览器下拉框选择器超时。后来分别通过可用 Maven、正确引用参数和修正选择器解决并重跑。保留失败记录有助于说明反馈与修复。没有逐步测试先行的完整历史，因此不能宣称已经严格实践了测试驱动开发的全部过程。

### 在 IDEA 或终端启动

## 十一 答辩时的表达与边界

最关键的回答顺序是业务目的、对应类与方法、实际校验、验证证据。例如老师问“为什么不会超退”，先解释剩余可退数量的公式，再指出退货服务锁定购买明细后检查差值，最后说明累计超退与并发退货测试都通过。

老师问“为什么要分层”，可以用改页面和改退款规则的区别说明：页面显示由模板和控制器处理，退款规则在服务与实体中维护，因此可以在不点击网页的情况下测试退款。老师问“为何改价不影响退款”，直接说明小票明细保留原单价，而退款从明细读取该值。

如老师追问尚未完成的功能，应说明当前边界，例如登录权限、银行卡、损坏商品、硬件打印和生产级迁移管理。可以描述未来改进思路，但要清楚区分现有代码与计划。二十组英语问题、英语示范回答和中文解析见单独的双语答辩材料。
