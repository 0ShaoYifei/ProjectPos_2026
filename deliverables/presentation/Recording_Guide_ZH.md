# 超市收银系统录屏指南

建议录制约七分半钟，主要讲解十五页英文演示文稿，在第十一、十二页切换到真实系统完成销售和退货。英文讲稿共七百六十三个口播词，按每分钟一百二十到一百三十词朗读，再留约一分钟操作停顿，通常可控制在六到八分钟。实际时长需要你试读计时；如果老师另有时限，以老师要求为准。

## 一 录制前的准备

- 打开英文演示文稿、英文讲稿、浏览器中的本机系统以及 GitHub 仓库。把无关窗口收起，关闭会弹出通知的无关应用。
- 在正式录制前完成 Maven 依赖下载、数据库密码设置和 GitHub 登录。检查麦克风音量、录制区域和分辨率，先录十秒测试声音与文字是否清楚。
- 选择一份运行实例。当前已验证有后台 JAR 实例监听 8080 端口；从 IDEA 再启动前，先确认并正常关闭你自己的旧 POS 实例，避免端口冲突。
- 新增的独立商品条码是 `REC-20261020-RICE` 与 `REC-20261020-MILK`。创建时两者库存各十件，单价分别为 6.50、3.80，尚未用它们自动创建新销售。
- 检查它们当前仍是有效商品且库存为十和十。练习会真实改变数量。如果已经练习过，用新的唯一条码创建另一组商品，并在讲稿旁记录新名称和编号。
- 原来的 DEMO 商品、POS-1 小票和 RET-1 退款是既有验证记录，不要删除、改写或反复当作空白小票使用。

## 二 开机与启动片段

先在服务管理界面确认 MySQL80 正在运行。打开 IDEA 中的 ProjectPos_2026 工程，展示项目和入口类 `ProjectPos2026Application`。运行配置中的密码应在录制前填写完毕，录制画面不要打开凭据值。

选择 IDEA 的运行按钮启动应用，或在工程终端执行 `.\mvnw.cmd spring-boot:run`。已有辅助脚本也可以通过 `powershell -NoProfile -File .\scripts\run-local.ps1` 启动。正式片段只需保留命令、启动完成日志与浏览器打开部分，等待下载依赖的长时间空白可以在你确实录制以后剪短。

等待日志显示服务器在 8080 监听且应用启动完成。浏览器访问 `http://127.0.0.1:8080/`，地址会跳转到商品列表。这就是当前实现的首页。录屏无需寻找额外的首页仪表盘。

可以把启动过程作为正式七分半钟讲解前的短准备片段，或把它放在第十一页演示开始时。若老师严格限制八分钟，建议只保留五到十秒启动完成和打开页面的画面。不要把旧启动日志伪装成本次重新运行。

## 三 演示文稿切换顺序

第一到三页说明项目、目标和业务规则；第四到六页说明个人增量开发、待办与真实检查点；第七到十页讲用例、架构、领域模型和数据库。每页只解释一到两个关键点，不逐字朗读技术报告。

第十一页先显示销售示例截图与金额，再切到浏览器操作。第十二页继续使用刚创建的小票做退货。完成后切回第十三页展示真实测试结果，第十四页切到 GitHub 展示提交与分支，最后回第十五页结束。

PPT 中 POS-1 和 RET-1 的截图是之前真实验证的例子。你本次录制将产生新的销售与退款编号，编号不同是正常的。口头说明“本次使用单独的录屏商品和新小票”，不要为了匹配旧截图去更改数据库编号。

## 四 商品页面与销售操作

先显示“Products”页面中两个独立商品的条码、单价和库存。若需要现场展示新增商品，点击“Add product”，填写新条码、英文商品名、单价和库存十，点击“Save product”。使用已有录屏商品时，直接选中它们即可。

点击导航“New sale”。在商品下拉框中选择录屏米，数量填二，点击“Add item”；再选择录屏牛奶，数量填一，再点“Add item”。页面合计应该为 16.80。停顿两秒，让观众看清购买明细和合计。

在“Cash received (CNY)”输入 16.79，点击“Complete sale”。显示现金不足英文提示后说明购物车仍保留。改成 20.00，再点“Complete sale”。成功后显示新小票，读出合计 16.80、现金 20.00、找零 3.20。

记下地址中的实际销售编号或小票的 POS 编号。展示“Print receipt”按钮，说明网页小票可以调用浏览器打印。为了保持演示流畅，本计划不打开打印对话框；如果老师要求打印 PDF，请在试录中练习该对话框并额外留出时间。

点击“Products”，指出米库存八、牛奶库存九。随后进入“Transactions and returns”，打开刚才的新小票；可以使用查找框输入实际销售数字编号。不要输入固定的旧编号一。

## 五 退货与库存恢复

在小票的“Handle returns”区域，找到“Purchased item”并选择刚购买的录屏米。退货数量先填三，原因填 `Recording demonstration`，点击“Record return and cash refund”。展示“超过剩余可退数量”的英文错误；这一步没有完成退款。

将数量改为一，保留原因，重新提交。成功提示应显示退款 6.50；退款记录区域出现本次新的 RET 编号。展示购买数量二、已退数量一、还可退数量一。

再次回“Products”，确认米库存由八恢复为九、牛奶仍为九。说明库存、累计已退数量和退款记录在同一事务中更新。现金仍需由收银员实际交还，系统没有银行卡转账接口。

不要为了展示重复提交而随意刷新一个已经换过请求标识的全新表单。同一请求去重与新表单的累计数量限制是两套保护。录制只需展示有效部分退货和超量拒绝，其他情形可以指向真实自动化测试。

## 六 测试与 GitHub 画面

回到第十三页，说明同一组二十一项测试分别在 H2 和真实 MySQL 上通过，另有十三项浏览器检查。若展示日志，打开保存的最终 Maven 日志，指出实际 Tests run、Failures、Errors、Skipped 和 BUILD SUCCESS。不要在短视频中完整重跑所有测试而留下长时间等待。

打开真实地址 `https://github.com/0ShaoYifei/ProjectPos_2026`。选择 main，进入提交历史，展示商品、销售、退货提交和合并记录，再展示保留的功能分支。第四阶段的 `feature/presentation` 是新增材料分支；只有已成功上传以后才在视频中说它已经发布。

GitHub Desktop 的“No local changes”说明当前没有待提交修改。有“Push origin”时，点击后等待推送完成，再展示网页上的最新提交。不要把资料里的旧机器人仓库作为本项目的证据，也不用展示任何登录凭据。

## 七 常见问题的处理

- 看到数据库连接错误时，先停止讲解，检查 MySQL 服务与本机环境变量；修复后重新录制该片段。
- 看到端口占用时，确认是否已经有本项目运行。只保留你确认的那一个实例，不要反复点击运行按钮。
- 合计不是 16.80 时，检查选择的是不是本轮录屏商品、数量是否合并过、购物车是否残留。开始新一轮时先清空购物车。
- 退一件被拒绝时，检查是否打开了正确的新小票、这条明细是否已经退过，以及原因是否填写。
- 第一次练习后库存通常为九和九；下一次若还要展示从十开始，应使用新的演示商品。不要覆盖旧交易来还原画面。
- PPT 截图与当前编号不同，可以直接说明“截图是之前的真实验证，本次录制创建新交易”。

## 八 可选中文口播

只有老师允许中文展示时再使用这一部分。正式英文展示仍以英文讲稿为准。下面按相同十五页顺序提供简明中文口播，你可以用自己的表达练习，并保留实际操作的停顿。

### 第一页 项目介绍

大家好，我来介绍我的小型超市收银系统，主要实现现金销售和退货。我会先介绍设计，再用真实系统展示一次收银和退款。整个项目由我个人完成，开发和测试证据都保留在工程中。

### 第二页 项目目标

这个系统最重要的目标是让库存和交易记录保持一致。成功销售后扣减库存并生成小票，接受退货后恢复库存并记录退款。英文表单与错误提示帮助收银员知道操作为什么被拒绝，以及需要修改什么。

### 第三页 功能需求

收银员可以维护商品、加入购物车、收取现金和查看历史小票。系统拒绝库存不足和现金不足的销售。退货必须关联原购买明细，数量不能超过剩余可退数量，并且使用购买时的价格，而不是商品现在的价格。

### 第四页 开发过程

我按商品、销售、退货和集成验证逐步实现系统，每个增量完成后执行测试，再根据失败结果修正。当前记录集中在同一次开发会话，因此我没有把这些步骤描述成已经完成了多天冲刺，也没有虚构多人团队活动。

### 第五页 待办与计划

原待办列表共有十八项，包含业务功能、验证和文档，这些项目都有完成依据。作业允许使用短冲刺，幻灯片中的三天窗口是后续复查和提交计划。我会把实际完成记录和计划日期清楚区分。

### 第六页 燃尽图

图上的每个点来自真实时间戳。纵轴是原待办剩余项数，横轴是经过的分钟。剩余项数最后从十八降到零，但各项难度不同，所以这不是工时或故事点图，也不能根据连线推断未记录时刻的完成数量。

### 第七页 用例

收银员是直接使用软件的参与者。销售和退货是两个核心目标，商品维护与交易查询为它们提供支持。顾客提供商品、现金或小票，收银员操作系统。报告中的系统顺序图把系统当作黑盒描述这些交互。

### 第八页 架构

模板负责显示，控制器负责接收请求与页面跳转，服务组织业务校验和事务，仓库访问并锁定数据库记录，实体保存状态与规则。这样的划分让退款逻辑不用写在页面里，也能通过服务测试检查业务行为。

### 第九页 领域与对象

系统的核心概念是商品、销售、购买明细和退货记录。一笔销售包含购买明细，明细保存原商品名和原单价。商品以后改名或改价，不会改写旧小票。小计与剩余可退数量由掌握这些信息的明细对象计算。

### 第十页 数据库

四张 MySQL 表保存这四类数据，购买明细通过外键关联销售和商品，退货记录再关联购买明细。结账和退货都有事务边界，库存与记录一起提交。行锁用于协调同时修改相同库存或可退数量的请求。

### 第十一页 销售演示

现在切到系统。我使用单独的录屏商品，两种商品初始库存各十件。加入两件米和一件牛奶后，合计是十六元八角。先输入少一分钱的现金，系统拒绝并保留购物车；再输入二十元完成销售，小票找零三元二角。回商品页可以看到库存变为八和九。

### 第十二页 退货演示

我打开刚才的新小票。先尝试退三件米，系统因只购买两件而拒绝。再退一件并填写原因，退款为六元五角。退款记录保存成功，米库存从八恢复为九，牛奶仍为九。原购买明细中还剩一件米可以退。

### 第十三页 测试

同样的二十一项自动化测试在 H2 和真实 MySQL 上分别通过，失败、错误和跳过数量都为零。还执行了十三项真实浏览器检查，并成功打包可运行程序。测试覆盖不足付款、超量退货、历史价格、重复请求和两个线程的数量冲突等情形。

### 第十四页 版本控制

这里展示实际 GitHub 仓库。商品、销售、退货和文档分支都有明确提交与合并记录，并保留功能分支。远程最初的 README 历史也通过合并保留下来。项目由我个人完成，分支代表工作主题，不代表虚构的其他开发者。

### 第十五页 结束

系统已经实现两个核心用例，金额、库存和交易记录能够一致更新，设计也能对应到真实代码和测试。当前仍是可信本地收银场景，账号权限、损坏商品和专用打印硬件属于后续改进。谢谢观看。
